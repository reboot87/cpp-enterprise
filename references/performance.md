# 高性能与低延迟

## 1. 指标定义(没有数字不算标准)

| 指标 | 定义 | 默认目标(仓库可覆盖) |
|---|---|---|
| 吞吐 | 每秒成功完成的操作数 | 不低于基线 |
| p50 / p99 / p999 | 端到端延迟分位 | p99 ≤ 2×p50,p999 ≤ 5×p50 |
| 排队时间 | 入队到开始处理 | 计入端到端,并单独上报 |
| 抖动 | p999−p50,或同负载下标准差 | 仓库目标 |
| CPU 效率 | CPU 时间/操作 | 不随吞吐线性恶化 |
| 内存 | 峰值 RSS、稳态漂移 | 24h 漂移 ≤ 5% |
| 启动 | 冷启动到可服务 | 仓库目标 |
| 热路径分配 | 每次操作的堆分配次数 | 稳态为 0,或显式预算 |
| 热路径 syscall | 每次操作的系统调用次数 | 显式预算 |

表中数值是默认起点,不是行业标准;以本仓库实测分布为准。

## 2. 测量方法(MUST)

- 只在 Release(开优化)下测;Debug 数字无效。
- 先 warmup 再采样;报告 p50/p99/p999 和吞吐,禁止只报平均值。
- 处理 coordinated omission:按固定速率发压,统计"应发未发"的排队时间,否则 p99 失真。
- 同一机器、同一构建、同一配置做前后对比;报告 CPU 型号、核数、编译器版本。
- 基线数据入库(如 `benchmarks/baseline.json`),CI 用同一硬件类别或专用 runner 对比。
- 单次运行不算结果:至少 3 轮,取中位数,并记录波动范围。

## 3. 设计规则

MUST:

- 热路径(请求处理、序列化、日志、哈希、循环)必须有 benchmark 或 profile 证据。
- 优化前先 profile(`perf`/VTune/Tracy),禁止凭直觉改。
- 不在持锁期间做 IO、分配、日志、序列化。
- 不写无上限的队列、缓存、缓冲、连接、线程;上限与溢出策略必须显式。
- 不在热路径做深拷贝、`shared_ptr` 复制、正则、locale 相关转换、同步日志。
- 不为了性能牺牲正确性;性能相关的 hack 必须注释原因和失效条件。

SHOULD:

- 批量 syscall(`writev`/`sendmmsg`)、批量提交、减少往返。
- 数据布局优先连续内存,热字段分开缓存行,避免 false sharing。
- 复用缓冲(池化)仅在有分配热点数据后做。
- 无锁结构只在有竞争证据且可证明正确时用;默认锁 + 减少临界区。
- 多 acceptor / `SO_REUSEPORT`,线程绑定与 NUMA 感知,按实测决定。
- 计时用单调时钟;高频时间戳考虑粗粒度缓存。

## 4. 低延迟专项

- 端到端延迟 = 排队 + 调度 + 处理 + IO;四段分别可观测。
- 尾延迟优先:排队是 p99 的主要来源;先限流和背压,再谈单请求优化。
- 避免队头阻塞:慢请求不能占住处理单元;超时和隔离必须生效。
- 批处理提升吞吐但会抬高 p99,必须用目标表约束上限。
- 禁止在请求路径做 DNS 解析、证书加载、磁盘同步写、动态库加载。
- 日志采样:热路径 ERROR 以上同步,INFO 异步或采样。

## 5. 门禁

| 检查 | 阈值默认 | 说明 |
|---|---|---|
| p99 回归 | > 10% 失败 | 相对基线,同硬件 |
| 吞吐回归 | > 5% 失败 | 同上 |
| 峰值 RSS | 超目标失败 | 目标见 `docs/nfr-targets.md` |
| 24h soak | 内存单调增长失败 | 需长稳任务,可夜间跑 |
| 热路径分配数 | 超预算失败 | 用计数器或分配钩子 |

阈值可按仓库放宽,但不能没有基线、不能永久豁免。

## 6. 诊断工具

`perf stat`/`perf record`、VTune、Tracy、heaptrack、valgrind callgrind、`strace`/ETW、HDR histogram、`wrk`/`hey`/自研压测器。

## 7. 容量与预算

- 每个模块有性能预算(延迟份额、内存上限、CPU 预算),写进 `docs/nfr-targets.md`。
- 预算按端到端目标倒推;p99 预算不能靠"平均下来够"。
- 容量规划:单实例容量 × 冗余系数 ≥ 峰值;扩容时间 < 业务增长时间。
- 架构或依赖变化后重测容量模型;定期压测验证。
- 每请求 CPU/内存成本随版本跟踪,异常上升视为回归。

## 8. 反模式

- 优化冷路径,热路径没数据。
- 用 Debug 或单次运行的数字下结论。
- 只报平均延迟,掩盖尾部。
- 压测机同时跑 CI、IDE、浏览器。
- 用"微基准快"代替端到端指标。
- 为省一次拷贝引入复杂生命周期和悬垂风险。
- 无上限缓存换来"看起来更快",随后 OOM。
