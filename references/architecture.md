# 架构与接口语义

## 1. 模块边界与依赖

- 模块按"变化原因 + 数据所有权"划分,不按文件类型划分。
- 分层:接口层 → 领域层 → 基础设施层;依赖只能向内,业务不依赖 IO 细节。
- 依赖必须显式、单向、可枚举;禁止跨层调用和循环依赖,依赖图入 CI 检查。
- 模块的公共头就是契约;实现可替换,契约变更走版本化。
- 禁止通过全局变量、单例、隐式初始化建立暗耦合。
- 跨模块调用只传值/不可变数据/稳定接口,不传内部结构指针。

## 2. 状态所有权与生命周期

- 每份状态只有一个所有者;其他方持有引用/句柄,并写明生命周期。
- 启动顺序固定:配置 → 日志 → 基础设施 → 业务;任一步失败立即退出(fail-fast),不留半启动状态。
- 关闭顺序与启动相反:停止接流 → 取消任务 → 排空 → 持久化 → 释放。
- 禁止在静态初始化阶段做 IO、注册回调、读环境变量。
- 请求级状态与进程级状态分离,禁止把请求数据挂在全局。
- 状态变更要有单一入口,便于加锁、审计和测试。

## 3. 一致性与幂等

- 每个数据明确一致性模型(强一致/最终一致),以及是否保证读己之写。
- 所有可能被重试的写操作必须幂等:幂等键、去重表或自然键。
- 跨服务写避免分布式事务;用 outbox/saga,并写明补偿与失败残留。
- 重复消息、重复回调、重复请求必须可安全处理。
- 状态机迁移显式,禁止隐式状态跳转。

## 4. API 设计

- 资源命名、方法语义、状态码、分页、过滤、排序、字段选择统一。
- 每个写接口支持幂等键;每个请求有 request_id;限流与重试语义写进契约。
- 错误格式统一(RFC 9457 或等价):`type`、`title`、`status`、`detail`、`instance`、`code`。
- 版本策略明确(URL 主版本或媒体类型);破坏性变更按 SemVer。
- 契约优先:OpenAPI/proto 入库,生成代码不手改,契约测试守护兼容性。
- 超时、取消、背压、分页上限写进契约,不靠调用方猜。

## 5. 错误分类学

| 类别 | 可重试 | 映射示例 |
|---|---|---|
| 输入错误 | 否 | 400 |
| 认证失败 | 否 | 401 |
| 授权失败 | 否 | 403 |
| 资源不存在 | 否 | 404 |
| 冲突/版本不匹配 | 视情况 | 409 |
| 限流 | 是(带退避) | 429 |
| 依赖暂时失败 | 是 | 503 |
| 依赖永久失败 | 否 | 502/500 |
| 内部错误 | 视情况 | 500 |

- 每个错误有稳定 `code`、可重试标志、用户消息、诊断信息。
- 用户消息不泄漏内部路径/堆栈/密钥;诊断信息只进日志。
- 维护错误码注册表(`assets/error-code-registry.md`),新增错误码要评审。

## 6. 降级矩阵

- 每个外部依赖列出:超时、失败阈值、降级动作、恢复条件、用户可见影响。
- 区分核心功能与非核心功能;非核心失败不影响核心路径。
- 降级必须可观测、可开关、可回滚;禁止静默降级。
- 模板见 `assets/degradation-matrix.md`。

## 7. 缓存

- 只缓存有明确失效策略的数据;缓存键包含格式版本。
- TTL + 主动失效;击穿用单飞/锁,雪崩加随机抖动。
- 负缓存有上限和短 TTL。
- 读己之写、强一致路径禁用缓存,或走显式失效。
- 缓存不是唯一数据源;丢失缓存必须能回源。
- 缓存命中率、回源量、失效失败可观测。

## 8. 消息与队列

- 默认至少一次投递,消费者必须幂等。
- 需要顺序时显式指定分区键/单队列,并说明乱序的容忍范围。
- 重试有上限与退避;最终失败进 DLQ,并有人处理。
- 消息带 schema 版本;不兼容变更走新 topic/新队列。
- 积压深度、消费延迟、DLQ 数量可观测并告警。

## 9. 反模式

- 循环依赖靠头文件顺序"碰巧"编过。
- 全局单例持有连接/线程/配置,无法测试也无法关闭。
- 用"最终一致"掩盖没有补偿方案的分布式写。
- 错误码每次随手新增,客户端无法稳定判断。
- 依赖失败直接 500,没有超时、降级、熔断。
- 缓存当成数据库,回源路径从未被测试。
- 消息重复消费靠"应该不会重复"。
