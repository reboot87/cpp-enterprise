# 可维护、可修改、可扩展

三者共用一条判据:**改动的代价**。代码规模阈值见 `quality.md` §2,这里只写系统级规则。

## 1. 可维护性

指标(仓库在 `docs/nfr-targets.md` 填具体数):

| 指标 | 默认目标 |
|---|---|
| 全量构建 | ≤ 5 min(大项目 ≤ 15 min) |
| 单测执行 | ≤ 2 min |
| 公共 API 文档覆盖 | 100% |
| 重复代码率 | ≤ 3% |
| 模块依赖环 | 0 |
| 新人上手到提交首个变更 | ≤ 1 天 |

规则:

- 模块按"变化原因"划分,不按技术分层硬切。
- 公共头只暴露稳定接口;实现细节留在 `.cpp`。
- 构建快:预编译头/模块/增量构建按需,不要靠"少编译点"换速度。
- 测试快且确定:慢测试分离到 nightly,主流水线保持分钟级。
- 文档三件套:README(能跑)、模块职责、ADR(为什么这样定)。
- 死代码、注释掉的代码、无用开关直接删,不留在仓库里。

## 2. 可修改性

指标:

| 指标 | 默认目标 |
|---|---|
| 常规功能改动的文件/模块数 | ≤ 6 |
| 修改一个行为需要的重新构建范围 | 单模块 |
| 破坏性 API 变更的弃用窗口 | ≥ 1 个次版本 |

规则:

- 改动局部化:同一变化原因只落在一个模块;出现"改一处要动五处"先重构。
- 依赖单向且显式;禁止通过全局变量、单例、隐式初始化制造暗耦合。
- 配置差异用配置表达,不用代码分支;部署差异不进业务逻辑。
- 高风险变更用特性开关,可灰度、可回滚。
- 公开接口变更必须版本化:新增不破坏、删除先弃用并保留窗口。
- 迁移脚本、数据格式变更必须有向前/向后兼容方案。
- 提交保持小而完整:一个提交一个意图,可单独回滚。

## 3. 可扩展性

扩展点必须先有契约,再有实现:

- 每个扩展点有稳定接口(SPI)和版本号;插件 ABI 遵循 SemVer。
- 用注册/发现(注册表、工厂、配置表)替代硬编码 `switch`/`if-else` 链。
- 新功能优先加在既有扩展点;必须改核心时,先加扩展点再实现。
- 扩展有隔离:插件崩溃不拖垮进程(进程内沙箱或独立进程,按风险选择)。
- 扩展有资源预算:CPU、内存、超时、并发上限。
- 扩展有测试:新增插件不改核心即可接入,并有契约测试。
- 数据驱动优于代码驱动:路由、策略、阈值优先走配置。
- 向后兼容:旧配置、旧插件、旧数据在新版本仍可用,或给出迁移工具。

## 4. 文档体系

| 文档 | 内容 | 更新时机 |
|---|---|---|
| README | 用途、构建、运行、验证命令 | 入口变化 |
| 架构文档 | 模块边界、依赖图、关键流程(C4 L1/L2) | 结构变化 |
| 模块 README | 职责、对外接口、失败语义 | 接口变化 |
| API 参考 | 公共头注释生成的文档 | 每次接口变更 |
| ADR | 重要决策与权衡 | 决策时 |
| Runbook | 部署、故障处理、回滚 | 见 `observability.md` |
| CHANGELOG | 版本变更与迁移 | 每次发布 |
| CONTRIBUTING | 构建、测试、评审、提交规范 | 流程变化 |

- 文档与代码同仓、同评审;过期文档直接删或改,不留"仅供参考"。
- 禁止把关键知识只放在 wiki、聊天记录或个人笔记里。

## 5. 评审与完成定义

- PR 有效改动 ≤400 行、一个意图;首轮响应 ≤1 个工作日。
- 关键模块(安全、并发、平台层、协议)至少两人评审;使用 `CODEOWNERS`。
- 评审关注设计、边界、安全、测试、可维护性;格式交给工具。
- 清单见 `assets/review-checklist.md`。
- 完成定义(DoD):全矩阵编译、测试通过、静态检查零新增、文档/CHANGELOG 更新、无新告警、风险已记录。

## 6. 技术债

- 每条债务登记:位置、原因、影响、偿还条件、issue 链接。
- 每个迭代预留 ≥10% 容量偿还;新增债务需评审同意。
- 禁止无 issue 的 `TODO`/`FIXME`;临时方案必须有到期时间。
- 债务趋势作为团队指标,不追求归零,追求可控。

## 7. 代码所有权

- 关键模块至少两名维护者;单人模块视为 bus factor 风险。
- 交接时更新模块 README 与 runbook,并安排一次结对讲解。
- 轮值评审,避免只有一个人能看懂关键代码。

## 8. 验证

| 方法 | 说明 |
|---|---|
| 依赖图 | 检测循环依赖和跨层引用(`include` 图工具) |
| 重复率 | jscpd / PMD CPD,阈值入 CI |
| 改动影响面 | 统计典型 PR 触碰的模块数,趋势上升即预警 |
| 构建/测试时长 | CI 记录并设上限 |
| 契约测试 | 每个扩展点一套,新实现直接复用 |
| API 兼容检查 | ABI/API diff 工具(如 abi-compliance-checker) |

## 9. 反模式

- 提前抽象:只有一个实现就建插件框架。
- 配置爆炸:每个分支一个开关,组合不可测。
- 扩展点无版本:插件升级即崩溃。
- 用宏和模板元编程制造"万能层",读者无法定位行为。
- 静默兼容:旧行为不报错也不提示,问题潜伏到线上。
- 为可扩展牺牲可读性:接口层数超过实际变化点。
