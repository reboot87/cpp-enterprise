# 第三方库与同能力多库

## 1. 能力表 + 单一实现

维护 `docs/deps-registry.md`(模板见 `assets/deps-registry.md`)。规则:

- 每个能力只允许一个默认实现;同一二进制里禁止出现两个同能力库。
- 引入任何库前写 ADR(`assets/adr-template.md`):需求、候选、许可证、体积、传递依赖、退出成本。
- 默认立场是 std/OS 优先;项目若声明零第三方依赖,该声明作为默认否决项。
- 替代实现只记录、不编译进同一目标。

## 2. 接缝设计

- 每个能力一个稳定接口头,业务代码只 include 这个头。
- 厂商头只能出现在 `src/adapters/<lib>/`;禁止出现在 `include/` 和 `src/core/`。
- 接缝处禁止泄漏厂商类型(`nlohmann::json`、`EVP_PKEY*`、`sqlite3*` 等)。
- 适配器只做翻译,不写业务逻辑。四点必须翻译干净:
  - 异常不越过接缝(转成 `std::expected`/错误码)
  - 内存谁分配谁释放,禁止跨接缝 `free`
  - 线程安全等级写入文档
  - 库的全局初始化显式且一次
- 可替换性指标:换实现时改动文件数 ≤ 适配器目录 + 一处工厂注册。

## 3. 选型评分卡

| 维度 | 权重 | 一票否决 |
|---|---|---|
| 许可证兼容 | 高 | GPL/AGPL 进入闭源产品 |
| 维护活跃度 | 高 | 12 个月无提交或无 issue 响应 |
| 安全记录 | 高 | 近两年未修严重 CVE |
| CVE 响应流程 | 高 | 无安全联系方式 |
| 平台矩阵 | 高 | 不支持目标平台 |
| API/ABI 稳定性 | 中 | 无版本策略 |
| 传递依赖数 | 中 | 引入 ≥10 个传递依赖 |
| 体积/编译时间 | 中 | 明显拖慢构建 |
| 可替换性 | 中 | API 侵入业务代码 |
| 性能 | 中 | 必须实测,不看宣传数据 |
| 文档质量 | 低 | 无示例 |

## 4. 依赖管理

- 版本固定 + 校验:`vcpkg.json` manifest / Conan lock / FetchContent + `URL_HASH`;禁止 latest。
- 拷贝入库的库:记录上游 commit、补丁列表(每个补丁单独 `.patch`)、升级计划。
- 禁止构建时无校验下载。
- 生成 SBOM(CycloneDX/SPDX)和许可证清单,随发布物交付。
- CI 跑 CVE 扫描和许可证白名单校验。
- 第三方库的 stdout 输出必须接管或关闭,统一走项目 logger。

## 5. 合规与生命周期

- 许可证白名单:MIT/BSD/Apache-2.0 可直接用;GPL/AGPL/LGPL 需法务 + ADR;每个依赖记录 SPDX 标识。
- 生成 NOTICE/许可证清单并随发布物;CI 校验新增依赖已在白名单。
- CVE 修复 SLA:严重 ≤7 天,高危 ≤30 天,中危下个版本;超期需书面豁免。
- 依赖升级:每月例行升级;安全更新不等例行;升级后跑全量测试与压测。
- 禁止来源不明的二进制;二进制需哈希/签名校验。
- SBOM(CycloneDX)每次发布生成,保留 ≥ 支持窗口。
- 构建来源可追溯(SLSA 或等价);发布产物签名。
- 依赖 EOL/停止维护即进入替换计划,不等出事。

## 6. 替换验证

- 每个能力配"一致性测试",换实现跑同一套测试。
- 关键路径做影子对比(新旧并行,比对结果与性能)。
- 行为差异要有开关和回滚方案。

## 7. 判定口径(避免过度设计)

- 只有一个实现且不打算换的能力,直接调用,不建接缝。
- 只有真实存在"同功能多库"(平台差异、可选后端、构建裁剪)或替换成本高时,才引入接缝。
- 接缝建立后,只允许一个默认实现,其余编译期可选,且全矩阵构建通过。
